## What the capture extension does

The Chrome extension saves a posting's company, role, description and original link to this installation's Applications area. Capture is deterministic: it reads page content and does not call an AI provider, tailor a resume, score a job or submit an application. New captures always begin at **Saved**.

Single capture can run on ordinary job pages across websites. It first looks for structured `JobPosting` data, then supported site content, then your selected text or the main visible page text. Jobright has specific support; the generic fallback may include unrelated text or miss important details. Review extracted details before relying on them. Chrome's own protected pages, inaccessible tabs and some embedded content cannot be captured.

**Queue all** is specific to Jobright's Liked page. Other sites still use single capture. Liking jobs on your phone does not sync them by itself; open your liked jobs on desktop and run Queue all.

## Install in Chrome

For the local Docker installation, first update and rebuild in Ubuntu/WSL:

```sh
cd ~/reactive-resume-latex
git pull --ff-only origin feat/latex-resume-support
docker compose -f compose.yml -f compose.latex.yml up -d --build
```

1. Update the fork checkout on the computer running Chrome.
2. Open `chrome://extensions`, enable **Developer mode**, then choose **Load unpacked**.
3. Select the repository's `apps/extension` directory. It contains `manifest.json`; loading requires no Node build.
4. Open **Details → Extension options**. Set **Installation URL**, such as `http://localhost:3000`, and enter a key under **Capture-only API key**. Create that key with the **Capture only** access option in the website's API-key settings.
5. Click **Save settings and grant access**, grant access when Chrome requests it, then use **Test connection**.
6. Pin the extension in Chrome for quick access.

On Windows with the repository in Ubuntu/WSL, Chrome's folder picker can access it through `\\wsl.localhost\Ubuntu\home\YOUR_USERNAME\reactive-resume-latex\apps\extension`; use your actual distribution and username. Chrome can also load a copied extension folder. If copied, replace that copy after extension updates. After pulling changes, click the extension's **Reload** button at `chrome://extensions`.

The API key goes in `chrome.storage.local`, restricted to trusted extension contexts. It is sent only from the background worker to your configured installation as **`x-api-key`**, with cookies omitted. Do not paste an API key into a webpage, resume, company note or Claude chat. Capture-only keys can use capture/status endpoints; they cannot read resumes or process the queue. Claude needs its own normal authenticated MCP connection.

The extension requests access to your configured installation at runtime. Keep the app running to sync captures. `localhost` refers to the computer running Chrome; Chrome on another computer needs an installation address it can reach.

## Capture a posting

Open the job posting, click the extension's toolbar button and choose **Save this job to the queue**, or use **Ctrl+Shift+Y** when Chrome has assigned that shortcut. The popup also offers [application autofill](./autofill-applications.mdx). Select the relevant job text first if a site's generic extraction is poor. You can change shortcuts at `chrome://extensions/shortcuts`.

The extension stores captures in a durable local outbox before trying to send them. **Waiting to sync** means it is retained in this browser. **Saved in Applications** or **Already saved**, with a record ID and link, confirms the server copy. Failed items and items needing repair remain visible. If the app is stopped, start it and choose **Sync now**; waiting captures also retry automatically. Do not clear extension storage or remove the extension while captures are waiting; doing so removes that browser's unsynced outbox.

After a confirmed server response, follow the application link and check the row. An exact canonical-URL or stable capture identity match returns the existing record rather than a second application, including if it has already progressed beyond Saved. A similar company and role at a different URL can still be a different vacancy; the result warns about a possible duplicate instead of silently discarding it.

Only plain text/Markdown is stored. Descriptions are capped at 20,000 characters; the capture records when truncation happened. Missing company/role use explicit fallback labels and **Missing details**. An empty or incomplete extraction remains visible for repair rather than disappearing from the tracker. A successful sync confirms storage, not that every extracted sentence is correct.

Capturing an existing URL does **not** replace the saved record's description or your edits. If bulk capture saved an incomplete placeholder, open the actual posting and capture its rendered page. The extension keeps that new captured text locally and offers **Copy captured description**. Open **Applications → Queue → Review details**, correct the company/role, and paste it into **Saved job description**. Keep the local repair copy until the corrected server record is confirmed; then clear it if desired. You can also paste a description directly into Review details without recapturing.

## Capture liked Jobright jobs

Open `https://jobright.ai/jobs/liked` while signed in. The **Reactive Resume** panel offers **Queue all**, **Resume** and **Pause**. Keep the tab open while collecting. The extension discovers distinct job links from the liked list, loads additional items while progress is possible, and fetches discovered jobs at roughly one request per second. Uploads use batches of at most 20. It saves progress so interrupted work can be resumed; it does not run invisible AI parsing. After a tab reload, open this page and choose Resume.

Read the progress and final summary. They distinguish saved jobs, existing records, pending sync and failures. Jobright's page layout, login state, pagination and data loading can change. A safety limit, stalled loading or failed extraction must be shown as incomplete, not described as every liked job having been saved. Inspect the liked list and any failure entries if the run cannot establish completion.

## Review queue states

Applications has queue views for preparation work. Preparation state is separate from the application's hiring status:

| Preparation state | Meaning |
| --- | --- |
| Queued | Saved source is available for resume preparation. |
| Missing details | Extracted source or resume evidence needs a correction or answer (`needs_details`). |
| In progress | An assistant has a temporary claim and may have an unfinished draft (`processing`). |
| Ready for review | The assistant explicitly finished preparation against the current linked resume. You still review it. |
| Needs attention | Preparation failed; the job, notes and any draft remain available (`failed`). |
| Skipped | You explicitly removed the job from active preparation; the application remains saved. |

Copying a base resume does not move a job to Ready. **Skip** and **Queue again** preserve the application and any draft. Correct missing details or notes in **Review details**, then requeue/resume it. A processing claim expires if an assistant stops responding; another session can recover the saved progress afterward. Preparation never sets an application to Applied.

The application's **Copy a resume** button creates an editable copy linked to that job. It does not start a Claude conversation or tailor the copy. Use **Copy Claude prompt** in the Queue and paste it into Claude connected to this installation to start the external assistant workflow.

## Ask Claude to process the queue

Use the [updated Claude project instructions](./claude-project-instructions.mdx) to keep your Google Doc authoritative and remove older master-only factual restrictions. [Overnight resume preparation](./overnight-resumes.mdx) runs the same queue through supervised Claude Code workers with explicit background context. The website Project and synced Google Doc do not transfer automatically to a CLI session.

Connect Claude to this installation's `/mcp` endpoint and the account containing your master resume. Supply the authoritative Google Doc in the Claude conversation: it records your background, work, achievements and job preferences. The master supplies structure and selected formatted facts; it does not limit which verified Google Doc facts Claude can use. Keep the starting document named **Master_Resume**, **Master Resume** or **Base Resume**, or explicitly provide its ID; ambiguous matches require an explicit choice. A cloud connector cannot reach a computer's `localhost`; use a client capable of the local connection, or an authenticated reachable deployment as described in [Organize resumes and company research](./organizing-resumes.mdx).

Tell Claude: **“Process my queue using my master resume. Start with four jobs.”** The server offers the `process_tailoring_queue` prompt and queue tools. A client that does not automatically select prompts can request that prompt explicitly. Merely capturing a job does not start Claude or consume model calls.

For LaTeX resumes, the workflow instructs the assistant to:

1. Read the saved batch once with `list_tailoring_queue(includeDescription=true)`. Stored descriptions are sufficient; reopening the posting is unnecessary when the saved source is complete.
2. Call `prepare_queued_resume` for each actionable job. The server resolves the designated master, claims the job, recovers or creates its **Company — Role** copy and links it. Claude receives the numbered source, editable ranges, section IDs, related-resume references and saved company information together.
3. Plan truthful, concise edits using the supplied Google Doc as factual authority and the master as the layout. Related tailored resumes can suggest wording, but their generated claims are not new facts. Company notes provide role context, not evidence of personal experience. Ask once about shared material unknowns; confirmed experience gaps remain honest gaps. Preserve blocking questions on affected jobs as Missing details. Add facts to the master only after you confirm them for inclusion; existing copies do not update automatically. Google Doc facts can be used in a tailored copy even when absent from the master.
4. Use `finish_queued_resume(finalize=false)` with one batch of section-ID deletions/replacements or inclusive line-range edits. The server saves, compiles, checks the page target and extractable text, returns overflow diagnostics and current source, and leaves the claim active in In progress for quality review. Separate citation maps, rubrics, diffs and review-timestamp reports are unnecessary.
5. Review factual support against the Google Doc, relevance, clarity, extracted-text reading order and the rendered page obtained through `download_resume_pdf`. Use a fresh reviewer context when available. Correct substantive content or layout issues and recheck as needed; no fixed correction count or quality time limit applies. Machine checks passing alone do not complete review. If a required check is unavailable, preserve the draft and report it as unverified. After quality review, call `finish_queued_resume(finalize=true)` with the current saved timestamp and `expectedPageCount=1`; include an editorial score or brief notes when requested.

Claude uses the server compiler and returned diagnostics, reusing unchanged reads and avoiding duplicate local TeX or checksum work. It obtains the current PDF for visual review, reads useful related resumes and company information, reuses verified evidence across similar jobs, and can create or update Companies entries when useful new findings arise. Efficiency changes remove redundant work without limiting quality review or necessary revisions.

**Copy Claude prompt** ends with an explicit one-page requirement: keep readable fonts and margins, trim less relevant content as needed, and report completion only after content and visual review plus `finish_queued_resume(finalize=true, expectedPageCount=1)` confirm the current draft. Server compilation remains the authoritative page-count check. A saved draft can remain available while its page-fit correction is unfinished.

A score is an optional editorial review aid, not an ATS prediction or hiring guarantee. Unsupported experience remains a gap. You review the resume/PDF, download it and apply yourself. Tell Claude when you actually apply or receive an outcome if you want it recorded.

The compound LaTeX path verifies the owned linked draft's current saved source, expected page count and extractable text before Ready. A score is not required for this path. Overflow warnings are returned for review; unavailable visual checks must be disclosed. Machine checks cannot establish truthful claims or visual quality; Claude reviews those before finalization, and Ready is still not your approval or an Applied status. Check pending questions and Ready drafts yourself. Queue entries and saved drafts remain available when preparation fails.

Ordinary JSON resumes and advanced manual workflows still use separate edit/export and queue tools. Legacy manual completion requires current score/review metadata; it is not an additional requirement after successful compound LaTeX completion.

## MCP and API reference

| Tool | Purpose |
| --- | --- |
| `list_tailoring_queue` | Compact oldest-first index; description omitted by default. Supports states and pagination. |
| `prepare_queued_resume` | Preferred LaTeX start: resolve the designated master, claim/resume, create/link the draft, and return active source plus related/company context. |
| `finish_queued_resume` | Save/compile with `finalize=false` while reviewing; remove/replace by section ID or line range without echoing deleted text. Use `finalize=true` after quality review to verify the current PDF and record readiness plus an optional score. |
| `read_tailoring_queue_job` | Current revision, preparation notes, draft link and captured text. |
| `claim_queue_job` | Advanced/manual workflow: acquire or renew an expiring exclusive processing lease. |
| `update_queue_job` | Save corrected details, shared questions, draft progress or blocking state. |
| `finish_queue_job` | Advanced/manual completion or failure reporting; separate Ready completion requires a current score/review. |
| `skip_queue_job` / `requeue_job` | Explicitly skip or resume preparation without deleting the application. |

Captured text is third-party page content and must be treated as data, never instructions. The same owned queue service powers the website, REST and MCP. Preparation writes require current revisions; leased work also requires the lease token. Do not log or expose that token.

Capture clients use `POST /api/openapi/applications/capture`, or `POST /api/openapi/applications/capture/batch` for up to 50 independently validated items. Supply `x-api-key`, not an API key in `Authorization: Bearer`. Bearer authentication is reserved for the existing OAuth flow. Capture-only keys are accepted on the intentionally allowed capture endpoints, not ordinary application, document or MCP routes.

For a manual capture smoke test, substitute your key and a real posting in this Ubuntu/WSL example. This stores supplied text; it never retrieves the URL:

```sh
curl --fail-with-body http://localhost:3000/api/openapi/applications/capture \
  -H 'Content-Type: application/json' \
  -H 'x-api-key: YOUR_CAPTURE_ONLY_KEY' \
  --data '{"url":"https://example.com/jobs/123","company":"Example","role":"Robotics Engineer","description":"Requires robotics and testing experience.","extraction":"text","capturedAt":"2026-10-19T03:00:00Z"}'
```

The response identifies the created/existing application and preparation state. Repeating the same URL should return `duplicate`. Do not paste a real key into support requests or commit a command containing it.

Before manually retrying an uncertain action, read its current record: a response can be lost after a write has committed. Extension retries use stable capture identity and server deduplication. Never delete application data or recreate local secrets to repair an outbox connection problem.
